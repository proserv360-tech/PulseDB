# Alert message format

Every alert PulseDB sends uses one structure, whatever the category. A rule
supplies the affected objects and their measurements; the pipeline does the
rest — one incident per object, priority, owner, SLA, rendering.

Source: `services/alertFormatter.ts` (shape and renderers),
`services/incidentService.ts` (incidents), `services/alertService.ts` (rules
and the firing path).

---

## Template

```
[SEVERITY] <Rule name>
Incident: <INC-YYYYMMDD-NNN>          ← only when the alert covers ONE object

<one-line summary — how bad, at a glance>

Incident ID       Database   Schema  Object   Metric  Priority  Owner  Status  AI Fix Suggestion  Detected At
────────────────  ────────   ──────  ──────   ──────  ────────  ─────  ──────  ─────────────────  ───────────
<one row per affected object>

Suggested fixes:
Target                          Action              Why
──────────────────────────────  ──────────────────  ────────
<INC-id>  <object>              <action>            <priority>

SQL:                                   ← Slack only, and only when a statement exists
<runnable, quoted statements>
```

Five parts, always in this order:

| Part | Purpose | Omitted when |
| --- | --- | --- |
| Title | `[SEVERITY] Rule name` | never |
| Incident line | the number to quote | the alert covers more than one object — the numbers are in the table |
| Summary | the old one-liner; answers "how bad" before anyone reads a table | the rule supplies no message |
| Incident table | one row per affected object | never |
| Suggested fixes | keyed by incident number so a fix matches its row | no object has a suggestion |
| SQL | statements, unpadded, ready to copy | no object has `fixSql` |

## Where each rendering goes

| Surface | Columns | Renderer |
| --- | --- | --- |
| `alerts.message`, email, in-app UI, PagerDuty, webhook | all 10 | `renderPlainText()` |
| Slack | 6 (compact) | `renderSlackBlocks()` |

Slack drops to `Incident · Object · Metric · Priority · Owner · Status`. Ten
columns is ~160 characters; a Slack code block is about 40 wide on mobile, so
the full set wraps into noise and becomes worse than the one-liner it replaced.
Database is dropped because it is constant across an alert; the fix text and
timestamp because they repeat below or don't change the decision. Owner and
status stay — they are what a reader triages on.

Slack also carries a plain `text` fallback (`:rotating_light: CRITICAL: High
Table Bloat`). That drives the notification preview and screen readers, both of
which are blind to blocks.

## Worked examples

All generated by running the engine — not hand-written.

### Many objects, mixed priorities and owners

One rule evaluation, two incidents, two teams, two different remediations and
two different deadlines.

```
[CRITICAL] High Table Bloat

2 tables with high bloat detected. Worst: orders (62%)

Incident ID       Database      Schema  Object         Metric  Priority  Owner     Status  AI Fix Suggestion       Detected At
────────────────  ────────────  ──────  ─────────────  ──────  ────────  ────────  ──────  ──────────────────────  ────────────────
INC-20260729-001  MarketTimeDB  public  orders          62.0%  critical  DBA Team  open    VACUUM (FULL, ANALYZE)  29/07/2026 14:19
INC-20260729-002  MarketTimeDB  crm     customer_logs   38.0%  medium    Data Eng  open    VACUUM ANALYZE          29/07/2026 14:19

Suggested fixes:
Target                               Action                  Why
───────────────────────────────────  ──────────────────────  ────────
INC-20260729-001  public.orders      VACUUM (FULL, ANALYZE)  critical
INC-20260729-002  crm.customer_logs  VACUUM ANALYZE          medium
```

### One object, instance-wide metric

Connection usage has no table or schema, so the object is the database itself.
It still gets an incident, an owner and an SLA — instance-wide metrics are not
second-class. Note the `Incident:` line, present because there is exactly one.

```
[CRITICAL] High Connection Usage
Incident: INC-20260729-001

Connection usage at 97.0% (97/100)

Incident ID       Database      Schema  Object        Metric  Priority  Owner     Status  AI Fix Suggestion                      Detected At
────────────────  ────────────  ──────  ────────────  ──────  ────────  ────────  ──────  ─────────────────────────────────────  ────────────────
INC-20260729-001  MarketTimeDB  —       MarketTimeDB   97.0%  critical  DBA Team  open    Add PgBouncer / raise max_connections  29/07/2026 14:20
```

### Non-numeric measurement

A PITR that isn't feasible has no lag figure. It displays as `not feasible` and
ranks critical rather than falling to `low` on a missing number — absent data
here means worse, not unknown.

```
[CRITICAL] PITR Window Below RPO Target
Incident: INC-20260729-004

PITR not feasible for connection 4: no base backup

Incident ID       Database      Schema  Object              Metric  Priority  Owner     Status  AI Fix Suggestion     Detected At
────────────────  ────────────  ──────  ────────────  ────────────  ────────  ────────  ──────  ────────────────────  ────────────────
INC-20260729-004  MarketTimeDB  —       connection 4  not feasible  critical  DBA Team  open    Restore backup chain  29/07/2026 14:20
```

## The Metric column

The only thing that varies between categories. Columns never change.

| Rule | Metric label | Critical | High | Medium |
| --- | --- | --- | --- | --- |
| `high_bloat` | Bloat % | ≥ 60 | ≥ 40 | ≥ 20 |
| `vacuum_overdue` | Dead % | ≥ 40 | ≥ 25 | ≥ 10 |
| `high_connections` | Conn % | ≥ 95 | ≥ 90 | ≥ configured |
| `low_cache_hit` | Cache miss % | ≥ 20 | ≥ 10 | ≥ 100 − target |
| `slow_queries` | Seconds | ≥ 300 | ≥ 60 | ≥ configured |
| `plan_regression` | Slower % | ≥ 500 | ≥ 200 | ≥ 50 |
| `replication_lag` | Lag (MB) | 10× configured | 4× configured | ≥ configured |
| `blocking_locks` | Locks | 5× configured | 2× configured | ≥ configured |
| `disk_space_warning` | Size (GB) | ≥ 500 | ≥ 200 | ≥ 50 |
| `pitr_rpo_breach` | Behind (h) | ≥ 24 | ≥ 6 | ≥ 1 |

`mapPriority()` ranks **ascending** — higher is worse. A metric where lower is
worse must be inverted before it reaches the pipeline. Cache hit ratio is the
example: it is stored and ranked as miss %, because storing the displayed
number would have ranked the worst cache performance as `low`.

The lowest band is the existing configured threshold, so nothing started
alerting that wasn't already. The higher bands only change how urgent it looks.

## Priority, severity and SLA

Two scales, deliberately.

- **`priority`** — `critical` / `high` / `medium` / `low`. Human triage. Drives
  the SLA and what the table shows.
- **`severity`** — `info` / `warning` / `critical`. Machine routing.
  `notification_destinations.min_severity`, `BaseNotifier.accepts()`, the
  `alerts` CHECK constraint and the Prisma model all speak it.

Derived from one another in `incidentService`; never set independently.

| Priority | Severity | SLA target | Escalates after |
| --- | --- | --- | --- |
| critical | critical | 4 hours | 4 hours |
| high | critical | 24 hours | 24 hours |
| medium | warning | 3 days | 3 days |
| low | info | 7 days | 7 days |

`medium` maps to `warning`, not `info` — `info` is below the default
`min_severity` of every destination, so mapping it there would mean medium
incidents notify nobody.

Targets live in `pgmonitoringtool.incident_sla`, per org, `org_id = 0` being
the built-in default. Change them with an UPDATE; no code change.

## Incident lifecycle

`status` is the incident; `fix_status` is what happened to the database. They
are separate because a VACUUM can be applied and not yet verified while the
incident is still being watched.

```
open ──▶ investigating ──▶ identified ──▶ in_progress ──▶ monitoring ──▶ resolved ──▶ closed
                                                                             ▲
   fix_status:  pending ──▶ applied ─────────────────────────────────────────┘
                              └──▶ verified   (resolves the incident)
                              └──▶ failed
```

- `applied` moves an untouched incident to `monitoring`.
- `verified` resolves it — the only signal the condition is genuinely gone.
- `autoCloseStale()` resolves incidents whose condition stopped firing, and
  promotes `applied` to `verified` when it does.
- `escalateOverdue()` bumps `escalation_level` past the SLA and re-notifies at
  `critical` regardless of the incident's own priority, so an ignored medium
  incident isn't filtered out by destinations that drop warnings.

Escalation bumps a level, never the priority: priority describes the problem,
escalation describes our failure to deal with it.

Every transition writes to `incident_audit_trail` — append-only, with actor,
action, note and any statement run.

## Incident numbers

`INC-YYYYMMDD-NNN` — date plus a counter that resets daily, from
`pgmonitoringtool.next_incident_id()`.

Recurrence is keyed on a fingerprint of `category:connectionId:ruleId:objectKey`.
While an incident is open, a re-fire bumps `occurrences` and `last_seen_at` on
the same row rather than minting a new number, so one number refers to one
problem for its whole life. A partial unique index enforces this. Once closed,
the same fingerprint may open a fresh incident.

**Expect gaps.** `INSERT ... ON CONFLICT` evaluates the default before it
detects the conflict, so a re-fire that merely touches an existing incident
still consumes a number. Normal for ticket systems; a gapless counter needs a
table lock on every insert. Read nothing into the distance between two numbers.

## Ownership

`incident_ownership_rules` matches an object to a team. Patterns are SQL `LIKE`,
so `audit%` or `%` for any. Most specific wins; category-scoped rules outrank
object-scoped ones, on the reasoning that "all reliability alerts go to Infra
Ops" is a deliberate routing decision.

```sql
-- catch-all
INSERT INTO pgmonitoringtool.incident_ownership_rules
    (database_pattern, schema_pattern, object_pattern, owner)
VALUES ('%', '%', '%', 'DBA Team');

-- a schema
INSERT INTO pgmonitoringtool.incident_ownership_rules
    (database_pattern, schema_pattern, object_pattern, owner)
VALUES ('%', 'audit', '%', 'Data Eng');

-- one table in one database
INSERT INTO pgmonitoringtool.incident_ownership_rules
    (database_pattern, schema_pattern, object_pattern, owner)
VALUES ('MarketTimeDB', 'sales', 'transactions', 'Infra Ops');

-- every alert of a category, wherever it happens
INSERT INTO pgmonitoringtool.incident_ownership_rules
    (database_pattern, schema_pattern, object_pattern, category, owner)
VALUES ('%', '%', '%', 'reliability', 'Infra Ops');
```

No match means `owner IS NULL`, displayed as `Unassigned`. That is deliberate —
an unowned incident is honest, and better than inventing an assignee.

## Adding a rule

A rule joins the format by declaring five things. Nothing else changes.

```js
{
    id: 'index_unused',
    name: 'Unused Index',
    category: 'maintenance',
    severity: 'warning',           // fallback only

    objectType: 'index',           // table | index | query | database | replica | connection
    metricLabel: 'Idle days',      // the Metric column header
    thresholds: () => ({ critical: 90, high: 30, medium: 7 }),

    condition: (metrics) => (metrics.unusedIndexes || []).length > 0,

    objects: (metrics) => (metrics.unusedIndexes || []).map((i) => ({
        schema: i.schema,
        object: i.index,
        metricValue: i.idleDays,               // number; ascending = worse
        metricDisplay: `${i.idleDays}d`,
        fixSuggestion: 'DROP INDEX CONCURRENTLY',
        fixSql: `DROP INDEX CONCURRENTLY "${i.schema}"."${i.index}";`,
        detail: `${i.sizeMb} MB, never scanned.`,
    })),

    message: (metrics) => `${metrics.unusedIndexes.length} unused indexes`,
}
```

`message` stays as the fallback for the case where every incident write fails —
a notification without incident numbers beats silence. The monitoring loop logs
a warning whenever it takes that path, so the fallback can't quietly become the
default.

`tests/alertRuleCoverage.test.ts` parameterises over the rule list, so a rule
added without `objects()` fails the suite immediately.

### Choosing an object

One incident per **thing you would fix separately**. Four bloated tables might
belong to three teams and be fixed at different times, so they are four
incidents. Connection saturation is one thing, so it is one incident whose
object is the database.

Pick an object name that is **stable across firings**. Slow queries key on
`queryid`, not the query text — text changes with parameters, and an incident
keyed on it would reopen on every execution.
